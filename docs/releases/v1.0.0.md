# v1.0.0 · 部门与数据权限管理微前端首个稳定版

G2rain（谷雨）是面向企业的开源智能体平台，连接模型、知识与业务工具，并提供 SaaS 基座和应用开发工具链。智能体平台与智能客服已开源；商业化能力仍在规划中。`g2rain-department-app` 只是在该平台中提供部门、部门成员关系和数据权限模型/字段/元数据/小组/规则配置界面的 Vue 3 微前端；它不提供部门数据持久化、最终授权、认证、网关转发或主壳治理。这些分别由 `g2rain-department`、IAM、Gateway 和 main-shell 负责。

## 交付、构建与镜像

- 项目版本：`1.0.0`；事实源为根 `package.json`（锁文件与 `docs/project.yaml` 已同步）。许可证为根目录 Apache License 2.0，OCI 许可证标签为 `Apache-2.0`。
- 构建要求：Node.js `>=22` 与 npm。完整本地/CI 源码验证是 `npm ci --legacy-peer-deps && npm run build`；项目没有独立 `test` 或 `lint` 脚本。
- 镜像：`ghcr.io/g2rain/g2rain-department-app:1.0.0` 与 `ghcr.io/g2rain/g2rain-department-app:sha-<完整提交 SHA>`；不会发布或更新 `latest`。
- 镜像以 Node.js 22 构建，运行时是 OpenResty；入口 `/docker-entrypoint.sh`，声明端口 `8080`，实际监听 `SERVER_PORT`（默认 `80`）。OCI source、url、title、version、revision 和许可证均写入 Dockerfile。

## 发布顺序与 GHCR

1. 按 `feature/* → develop → main` 将本说明、工作流和发布改动合入 `main`，并在待打 tag 的提交完成本地验证。
2. 在该 main 提交创建并推送 `v1.0.0`。工作流会严格校验格式、main 历史、本文件非空以及 `package.json` 版本一致。
3. 工作流使用 `GITHUB_TOKEN`，仅在 `1.0.0` 和 `sha-<完整提交 SHA>` 都已推送后才在 Summary 报告发布成功。登录成功、构建成功或部分 layer 上传均不代表发布成功。
4. 首次成功推送后，在 GitHub **Package settings → Change visibility → Public** 将包设为公开；受组织策略限制时联系管理员。若已有包，遇到 GHCR `denied` 时先在 **Package settings → Actions access** 授予本仓库写权限，并检查组织 Packages 策略。

发布不创建 GitHub Release、不部署服务，也不进行匿名拉取。公开后可单独执行 `docker pull ghcr.io/g2rain/g2rain-department-app:1.0.0` 验证匿名拉取。

## 镜像内容、安全与验证边界

最终镜像包含编译后的静态资源、OpenResty/Nginx 配置模板、Lua 签名实现和 luaossl；不包含源代码、Node 依赖或构建阶段文件。`.env` 被排除，而 `.env.production` 的公开 `VITE_*` 构建配置会编译入静态资源；检查时未发现已跟踪的 Token、私钥或真实凭据，仍不得把生产密钥或私有地址写入 `VITE_*`。`lua/keys/*` 已被 Docker 构建上下文排除，仅保留 README。生产环境必须通过 Secret 或只读挂载把 DER 私钥/公钥、IAM key ID 与 IAM 公钥放入 `/usr/local/openresty/nginx/lua/keys`，并通过环境变量注入 Gateway、IAM、Context Path、端口和 SSO 配置。不要把 Token、私钥、生产地址或其他凭据提交、写入镜像或通过命令行暴露。

本次发布准备会验证工作流语法、版本/镜像/文档一致性，并应执行本地源码构建；它不证明浏览器的独立/qiankun 集成、Gateway/IAM/SSO 连通、密钥挂载、容器启动、GHCR 推送、匿名拉取、在线演示或真实部署。各项结果必须分别记录，不能互相替代。

## 已知限制

- 项目没有独立 `test` 或 `lint` 脚本；CI 的自动验证范围仅为按锁文件安装后的类型检查与 Vite 构建。
- Dockerfile 不运行 `vue-tsc` 或 `build:config`，因此容器构建成功不能替代完整源码构建、资源差异审查或独立/qiankun 集成验收。
- 公开镜像、GHCR 权限、匿名拉取、容器运行与实际环境部署均需在首次 tag 推送后由维护者分别确认。
